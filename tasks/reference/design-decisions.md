# gacalc design decisions (digest)

**Reference document** — a distilled index of the durable design decisions and their rationale, pulled from the archived task docs so they're not lost in the don't-trawl archive. Not a task; update in place. Last updated 2026-07-21.

Each entry: **what** was decided · *why* (the surprising/re-litigable part) · the archived task where it was decided. CLAUDE.md is the "what is true now"; this is the "why, and where it was settled." Paths are repo-relative under `tasks/archive/`.

---

## Representation & performance

- **`Gn` is the slow correct reference; `G1/G2/G3` are the fast path — deliberately, and `Gn` is NOT to be optimized.** Profiling showed eager `sympy.simplify` in `Gn.__post_init__` is ~100% of `Gn`'s cost (28.098 of 28.116s; one 𝒢₃ product builds 128 simplifying MultiVectors). The fix is *not* to speed up `Gn` — it's the oracle — but to add closed-form specialized classes derived from `Gn`'s own symbolic products (so "provably consistent"). Rejected: a float fast-path (needs tolerance equality, breaks exact symbolic tests) and a single Cayley-table `DenseEuclidean(n)` (DRYer but no named-component API). Also fixed the ABC boundary as *"touches the raw representation"* not *"transitively uses the product."* — `2026/06/03/specialized-multivectors.md`

- **Specialized classes are lazy (simplify only on equality/display); `Gn` is eager.** The whole speed win is (a) closed form + (b) *no* eager simplify. Consequence: a lazy class stores un-reduced coefficients (e.g. `B·B.dual()` stores `(cos²t+sin²t)·e₁₂₃`), which is why `.simplified()`/display-simplify exist. — `2026/06/03/specialized-multivectors.md`, `2026/06/12/graded-bivector-dual-simplify.md`

- **Generated value types are `frozen=True, slots=True` — immutable (decided 2026-07-23, reversing the earlier "deliberately NOT frozen").** `slots=True` removes per-instance `__dict__` (the base declares `__slots__=()` so slotted subclasses inherit none); it was a *historical oversight* that graded subtypes + `Scalar` lacked it (added when only the full classes existed). `frozen=True` was held off for a year-long stretch because *modelviewprojection* mutates vectors in place (`self.dir.x = -self.dir.x`) throughout its Code-the-Classics ports, so freezing is a **breaking change, not a hardening**; it was taken anyway because immutability removes the aliasing footguns wholesale (a multivector in a module constant, class attribute, or mutable default arg is no longer a hazard, and the basis constants `Vector2.e_1` … can't be mutated by accident) — the consumer converts to *rebinding* (`v = Vector2(-v.x, v.y)`), gated on a gacalc release. Known wart kept on purpose: a **field** write raises a clean `FrozenInstanceError`, but a **property** write (`v.x = …`) surfaces a confusing `TypeError: super(type, obj)…` (a Python 3.14 frozen+slots+property quirk) — dropping `slots` gives clean errors but loses the `__dict__`-free win, so `slots` stays. — `2026/07/23/investigate-frozen-generated-classes.md` (the freeze); earlier, for the `slots` history and the mutability rationale it overturned: `2026/06/27/graded-subtypes-slots-true.md`, `2026/07/08/subclass-preserving-generated-ops.md`

## Generated code (the codegen)

- **Generated modules moved OUT of git — reversing the original decision to commit them.** First committed (so a `pip install`ed student can *read* the closed-form source in `site-packages` — the pedagogy constraint), then 4 days later gitignored and generated at build time (`build_py` hook bakes readable `.py` into the wheel). The readability constraint still holds — build-time generation is the *rejected on-import Option 2*'s opposite: the wheel carries real source, no generator runs at install. Two gotchas: build-requires needs **numpy AND sympy** (the generator imports `base`→numpy), and numpy/sympy are genuine *runtime* deps regardless. — `2026/06/06/codegen-checkin-strategy.md` (original), `2026/06/07/build-time-codegen-dist.md` (reversal)

- **Generator builds Python `ast` nodes + `ast.unparse`, not string concatenation.** Correct-by-construction (no fragile regex rename — a `SymbolToAttr` NodeTransformer instead; `unparse` can't emit invalid code). Forced constraint: **AST has no comment nodes**, so byte-identity to the old hand-tuned output is impossible and the copyright/import header stays raw prepended text. Three approaches (minimal / template-splice / hand-built nodes) were each built and committed for comparison; hand-built nodes won, and the "less readable" verdict was *retracted* for a metaprogramming mindset. — `2026/06/07/codegen-via-python-ast.md`

- **The domain-agnostic node-builder DSL lives in `tools/astbuild.py`, separate from GA codegen.** Builders "know nothing about geometric algebra"; the split sharpens the boundary and makes the DSL independently inspectable. Naming convention is load-bearing: a builder's suffix predicts its return type (`*_method`→FunctionDef, `*_stmt(s)`→statement(s), `*_value`→expr). The `summed/result/unary_value` split is *kept un-merged on purpose* — it mirrors three genuinely-different cast/term-order policies. — `2026/06/07/gen-specialized-structure-refactor.md`

- **Graded/blade subtypes' return types are resolved symbolically at generation time, never from runtime floats.** A product's result type = smallest registered type whose blade-set ⊇ the *symbolic* support of the result, else widen to full `G_n`. This "kills the FP problem": `Vector×Vector→Rotor` (scalar+bivector) holds even when the scalar part is exactly `0.0` — "we never narrowed on a float." Primary motive is **pedagogy** (the dispatch table *is* the product table); speed is minor (~2.7× over full `G2`). Widen fallback targets the *same-dimension* full class; a shared dimension-agnostic `Scalar {()}` type keeps pure-scalar results from widening to `Rotor`. — `2026/06/06/graded-blade-subtypes.md`

- **A closed-form `sandwich(x)` (`R·v·R⁻¹`) is generated as its own derived op — no runtime grade projection.** Running the *whole* `R * x * R.inverse()` symbolically proves the `e₁₂₃` part cancels identically (the intermediate `R·v` genuinely has support `{1,3}`, which is why the plain product widens), so `resolve()` types it exactly as the operand with zero runtime projection. Uses the inverse form `R v R⁻¹` (true for any rotor, accepting rational `/|R|²` coefficients) over `R v R̃` (unit-rotor only). — `2026/06/08/derived-sandwich-operation.md`

- **Same-type generated ops emit the concrete class name — every value type is `@typing.final`, so no `type(self)`.** *Originally* all same-grade results used `type(self)(...)` for subclass preservation (`type(ShimVector2 + ShimVector2)` was losing the subclass), with widening/grade-changing results keeping the concrete registered class (`Vector2*Vector2→Rotor2` — "a subclass has no say over a different grade's class"). **Reversed for the graded types 2026-07-21** once it was confirmed that *nothing subclasses them* — the mvp pygame-`Vector2` use case was superseded by "use `gacalc.g2.Vector2` **directly**"; the graded value types + `ScalarN` were made `@typing.final` (`ty` enforces via `subclass-of-final-class`), emitting the concrete class (`return Vector2(...)`). **Extended to the full classes `G1`/`G2`/`G3` 2026-07-23** — a search confirmed nothing subclasses `G_n` either (the only subclass anywhere was the test asserting it was *possible*; mvp never references `G1/G2/G3`; the dimension-agnostic `Gn` in `gn.py` is the general representation). So `G_n` is now final too, the `result_spec.kind != "full"` construction branch collapsed, and the generated full class carries **no `type(self)`**. `construct_type_self` survives only as an unused general astbuild primitive. (`MultiVectorBase`'s own `type(self).zero()`/`from_blade_dict()` in `base.py` is **untouched** — that is cross-*representation* polymorphism, not subclass preservation.) — `2026/07/08/subclass-preserving-generated-ops.md` (original), `tasks/archive/2026/07/22/finalize-graded-types.md` (2026-07-21 graded reversal), `tasks/archive/2026/07/23/investigate-final-full-classes.md` (2026-07-23 full classes).

- **The `match`-on-rhs dispatch matches on TYPE only, not by destructuring the rhs's components — investigated and declined 2026-07-23.** Rewriting `case Vector2():` (then reading `rhs.coeff_e_1` in the body) to `case Vector2(coeff_e_1=b_e_1, …):` (binding each field as a local) is *feasible* (keyword patterns need no `__match_args__`, so they work on the frozen+slots dataclasses) but is a net-neutral-to-negative lateral change: (1) it breaks the symmetric `self.coeff_e_1 * rhs.coeff_e_1` reading (→ asymmetric `self.coeff_e_1 * b_e_1`); (2) the `#1` same-type early-out is an `if`, not a `match` case, so it **can't** destructure — the identical same-type formula would then appear in two spellings in every product method; (3) it doesn't simplify the generator (`a_*`/self symbols can't be pattern-bound, so `SymbolToAttr`/`rename_map` stay, while `_match_class` gets *more* complex — complexity moves sideways); (4) verbose pattern headers for byte-identical runtime. Type dispatch is legitimate `match` use per CLAUDE.md, so `case Vector2():` stays. `Gn._geometric_product`'s `decrease_grade` already destructures **blade tuples** (structural list-patterns) — a different, in-idiom use. — `tasks/archive/2026/07/23/match-destructure-components.md`.

- **Generated fast-path dispatch was tuned against the real Code-the-Classics op-mix, not a synthetic guess.** Added an exact-type early-out (`if type(rhs) is <Self>`) before the `match` ladder, direct-field number arithmetic, and a closed-form `magnitude_squared`. Metrics were *required* to come from profiling 4 real workloads (same-type binary ops dominate; soccer's magnitude chain ≈1.7M of 3.9M calls). Hard constraint (Bill): the fix lives in the generator so *every* consumer inherits it — "never a hand-written shim revival." Reordering match arms by frequency was declined (marginal once the early-out hoists the dominant case). — `2026/07/18/generated-dispatch-fast-paths.md`

- **Additive terms in each generated component are ordered by grade (scalar→vector→…) via `term_grade_key`.** Pure readability (sympy's default sorts `e_12` before `e_2`); must not change computed values. LaTeX output left alone — `base.py` re-sorts blades itself. This work also established that the generator must self-format (raw output got committed once), so `main()` runs ruff on its own output. — `2026/06/05/modify-generated-code.md`

- **The generator's own pure logic is unit-tested (`tests/test_generator.py`), separately from its output.** Test the deterministic input→output pieces only transitively covered elsewhere — above all `resolve`/`product_result` ("the type follows the operation"). Deliberately *not* unit-tested: generated-class behaviour (conformance/graded suites own it), determinism (`check-generated` owns it), and the exact emitted *text* of whole methods ("brittle golden-file testing"). — `2026/06/27/unit-test-the-generator.md`

- **`make check-generated` is a make target (not a pytest test) and now checks determinism.** Regen mutates the working tree and is ~30s (𝒢₃ dominates) — wrong for the default fast `pytest`. Originally a git-diff drift guard on committed files; repurposed to "regen twice, assert byte-identical" once the files became gitignored. — `2026/06/06/regen-diff-ci-guard.md`, `2026/06/07/build-time-codegen-dist.md`

## Type system & typing

- **`Coef = int | float | sympy.Expr` is a concrete union, deliberately NOT the `numbers.Real` ABC.** `numbers.Real` arithmetic types as `_ComplexLike`, and ty then *rejects* `+`/`/`/`**` on it — which is what forced the old scoped `ty.toml` override on the generated rotor `sandwich`. Re-litigation guard: `numbers.Real | sympy.Expr` does **not** work either — it keeps the poisonous `numbers.Real` arm (probe-confirmed). Retyping to `Coef` deleted the override and let `sandwich` be a Liskov-compatible override returning the operand type. — `2026/06/11/restore-ty-on-generated-sandwich.md`

- **The generated rotor `sandwich` returns the operand type `_OperandT`, not `Self`.** "A rotor's sandwich of a vector is a vector, not the rotor — the old `cast(Self, …)` was a lie." ty accepts a subclass overload returning a non-`Self` type over a `-> Self` base (contra a natural but wrong assumption). — `2026/06/11/restore-ty-on-generated-sandwich.md`

- **Generated products/sums are typed precisely with `@typing.overload` on the operators themselves.** An earlier per-pair-free-function + generic-`match`-delegation approach was built (388 tests green) and *reverted* — it left the operators untouched, so `v2 * v2` still mistyped as `Vector2`. Overloading the operators directly fixes the operator. Impl returns broadened to `MultiVectorBase` (the one common supertype; `G2` was tried and rejected — the graded types are *siblings* of `G2`, not subclasses). Full rationale is in the sibling reference `tasks/reference/generated-product-typing.md`. — `2026/07/21/typed-product-helper-functions.md`

- **`base.project` narrows to the operand's grade/type instead of widening to `Gn`.** `P_B(A)=(A·B)B⁻¹` is grade-preserving in *value*, but the generic product widens the *type* (`Vector3 * Bivector3⁻¹` types as `{1,3}`→`G3` because a vector·bivector *could* carry grade 3). For a projection that grade-3 part is identically zero — "a vector wearing a `G3` tag." The `is_r_vector` branch rebuilds in the operand's own type. — `2026/06/12/project-grade-preserving-narrowing.md`

- **`magnitude()`/`inverse()` preserve numeric input (float→float), reversing an earlier "always sympify" fix.** First `inverse()` was routed through sympy to fix an exactness bug (`int ** -1` returns a `float`: `25**-1 == 0.04`). Then that was *reversed* for the numeric path because unconditional sympy poisoned pipelines — a rotated numeric vector got sympy coefficients, making mvp's GL matrices numpy `dtype=object` and `np.linalg.inv` throw. Final split is deliberate: **float→`math.sqrt` (float); int→`sympy.sqrt` (exact, so `sqrt(25)==5` and unit blades give `Rational`s); symbolic stays symbolic.** Do not reintroduce an unconditional `sympy.sqrt`/`sympify` (guarded by `tests/test_numeric_magnitude.py`). — `2026/06/06/inverse-exact-reciprocal-fix.md` (first), `2026/06/13/magnitude-numeric-for-numeric-input.md` (reversal)

- **The acyclic-layering invariant, and why `functions.py`'s TypeVar is unbounded.** `base.py` may import a *leaf* (imports nothing internal, representation-agnostic, cheap) but nothing at/above its layer. The only leaf is `functions.py`; its type parameter is **unbounded** rather than bound to `MultiVectorBase` precisely because binding it would force `functions.py` to import `base` and reintroduce the cycle — "that's the whole cost." — `2026/07/17/reassess-composable-function-interface.md`

- **`from __future__ import annotations` is emitted everywhere, with two carve-outs.** PEP 563 lets forward-ref quotes drop (floor is 3.13). But `MultiVectorFn = Callable[...]` **keeps its quotes** — it's a runtime assignment evaluated before the class exists, which PEP 563 doesn't affect. And a `@dataclass(slots=True)` with string field annotations is fine for field detection, but anything introspecting `__annotations__` for real types must be vetted. — `2026/06/06/future-annotations-drop-forward-ref-quotes.md`

- **Type annotations: annotate non-obvious locals; skip the obvious; don't fight the checker.** Codified cases worth knowing: `from_blade_dict` param is `Mapping[..., Coef]` not `dict` (**dict is invariant**, rejecting `dict[..., Symbol]` callers); `__iter__` is left *unannotated on purpose* (typing it `Generator[Coef]` makes `case [*sequence]:` in project/reject/reflect falsely match a lone multivector); reused-name locals (`sa`/`sb` bound to two types) stay inferred; polymorphic-over-`cls` locals are typed `MultiVectorBase`; generated-method *params* are deliberately not annotated (polymorphic operands — a missing annotation is `Unknown`, not an error). The generator's `cse` temporaries are unannotated to avoid stamping `: numbers.Real` on every arithmetic line. — `2026/07/18/annotate-local-variable-types.md`, `2026/06/06/add-python-types.md`, `2026/06/27/add-types-signatures-and-tools.md`

## API & conventions

- **The composable-function hierarchy splits by capability: `ComposableFunction` (no inverse) + `InvertibleFunction`.** One type was doing two conflicting jobs. mvp's Cayley-graph engine *requires* invertibility (walks edges backward) — a group axiom; display/compose don't. A `labeled(project)` with a raising-stub inverse was a runtime landmine (type-checks, then raises `NotInvertibleError` only when the graph walks backward). The split makes "projection used as a group generator" a **compile-time** type error. Returns are typed at `MultiVectorBase` (not `Self`) so `base` stays cast-free — caller casts at the use site (measured ~0 casts in real callers). — `2026/07/17/reassess-composable-function-interface.md`, and the interim `labeled` wrapper that surfaced the need: `2026/07/16/latex-labels-for-project-reject-in-pipeline.md`

- **Rotation factories are named by two axes: spec vs formulation.** `projection_rotation`/`rotor_rotation` share the from/to spec, differ by formulation; `plane_rotation` has a unique plane+angle spec. `rotate` (a bare verb that returns a function and misreads vs `rotor`) was removed and moved off the ABC to a free function in `transforms.py`; `rotor_from_vectors` **stays on the base** because it builds a *value*, not a transform. — `2026/07/16/relocate-rotate-and-rename-rotations.md`

- **`plane_rotation(a, b)` separates plane from angle — the API that fixed mvp's animation fight.** `rotate(from, to)` locks the angle to the two vectors ("no way to say same plane, varying angle"); `plane_rotation` returns `θ → InvertibleFunction` so interpolation falls out as `f(t·θ)`. The wedge-is-zero test *is* the linear-dependence test. It caches two copies of the unit bivector (exact + float-coerced) and picks per-θ to avoid a measured ~6× per-frame slowdown from sympy `Float` contamination; symbolic θ stays symbolic. Cost model deliberately splits factory-time / per-θ / per-application work so no θ-cache is needed. — `2026/07/09/plane-rotation-pretag-and-mvp-adoption.md`, `2026/07/09/upgrade-rotation-and-ctc-vector-mapping.md`

- **`plane_rotation` keeps callable label hooks (`latex_repr`); `rotor_rotation` had its dropped.** Not a contradiction: mvp actually overrides `plane_rotation`'s labels to brand per-axis rotations `RX_`/`RY_`/`RZ_` (with a test), so they're live API; `rotor_rotation`'s were dead parameters no caller ever set. — `2026/07/16/drop-unused-latex-args-from-rotor-rotation.md`

- **`InvertibleFunction` carries a `Linearity` tag (LINEAR<AFFINE<NONLINEAR); `to_matrix` uses it as a guard.** Int-backed enum so `compose = max(...)` *is* the lattice join; the tag is the tightest class that fits. LINEAR/AFFINE are exact under composition; NONLINEAR is a *conservative over-approximation* (a structural tagger can't see `f∘f⁻¹` collapse to identity). `to_matrix` **always emits homogeneous `(n+1)×(n+1)`** even for linear maps (graphics stores 4×4 throughout), via one unified `column i = f(e_i) − f(0)`; NONLINEAR (perspective) **raises** because the affine probe can't recover the projective last row. — `2026/06/08/classify-functions-linear-affine-nonlinear.md`, `2026/06/08/invertiblefunction-to-matrix.md`, `2026/06/12/to-matrix-build-by-columns.md`

- **`component(x)` was retired in favour of `coefficient(blade)`.** `component` *computed* `⟨A x̃⟩₀` (a product + grade projection) to recover a number the object already stores — and was sign-wrong for grade ≥2, a bug that hid because it was untested. `coefficient(blade)` is a thin direct `to_blade_dict()` lookup, correct for any grade. Guard: `to_blade_dict()[(1,2)]` is the coefficient itself, whereas `scalar_product(e_12)` is its *negative* — `scalar_product` is kept as the genuine scalar product `⟨A B⟩`, not a coefficient reader. — `2026/06/12/retire-component.md`

- **Transforms are representation-preserving (`G1/G2/G3`) by late-binding the basis from `type(vector)`.** The representation-binding was far narrower than it looked — only ~3 basis-bound factories baked in module-level `Gn` constants; most transforms already preserved type. Chose late-binding (Option A) over per-class generator copies (heavy duplication) and ABC classmethods (would pull the book-shared `InvertibleFunction` into `base.py`). Scales to any future algebra for free via the interchange protocol. — `2026/06/05/investigate-how-to-extract-translate-etc.md`

- **The 2D-only planar transforms were *removed*, not guarded.** Applying planar `rotate(θ)` to a `G3`/`Gn` vector with an e₃ component silently makes a mixed-grade result — and types can't catch it (`Gn` is one type spanning all dimensions). The resolution: these were modelviewprojection artifacts with no GA-pedagogy weight, and GA rotation is already covered by the rotor — so removing them moots the whole hazard. — `2026/06/06/clarify-2d-only-transforms.md`

- **Build multivectors from basis vectors (`3*Vector2.e_1 + 4*Vector2.e_2`), not blade-dict literals or positional constructors — in teaching-facing code.** Reads like the mathematics and scales uniformly to bivectors/rotors. The positional constructor is **not** deprecated (natural output of `from_blade_dict`); this is a style preference for demos/notebooks. Key exceptions left alone: product tests (rebuilding via the operation under test = circular ground truth), dense benchmark dicts (read worse as basis combos), and the chapter that *teaches* the constructor itself. — `2026/06/06/basis-vector-construction.md`, `2026/07/18/prefer-basis-vector-construction.md`

- **`Vector2.e_1` was accidentally `0`; the fix frees `e_n` for class constants by renaming fields to `coeff_e_1`.** The `0` was a dataclass field-default leak with no use. One name (`e_1`) needed two meanings — class access → basis vector, instance access → coefficient — which descriptors/metaclasses could do, but renaming the field to `coeff_*` lets a plain class constant serve *both* with no magic. Blast radius contained because all cross-representation interaction goes through the tuple-keyed blade-dict interchange, not field names. — `2026/06/07/graded-class-e_n-zero-vs-basis-vector.md`

- **`m` and `b` are a protected exception to "descriptive over terse."** `translate(b=...)`/`uniform_scale(m=...)` are named for `f(x)=m·x+b` (`b` shift, `m` stretch) so a student meets the transforms through an equation they know. Recorded in *both* CLAUDE.mds precisely so a future naming pass doesn't "fix" them to `offset`/`factor`. Keyword form is used at teaching-facing call sites only; library internals stay positional. — `2026/07/21/mx-plus-b-named-parameters.md`

- **`exp()` dispatches by grade structure, not by the sign of A² — that's the payoff of hardcoded-Euclidean.** galgebra's `exp(hint='-'/'+')` exists because arbitrary signatures leave a symbolic A²'s sign undecidable; in Euclidean 𝒢ₙ a grade-r blade has `A² = (−1)^(r(r−1)/2)|A|²`, so trig-vs-hyperbolic is decided structurally and no hint parameter exists. Two load-bearing details: the result is built with *dispatching arithmetic* (`Â·sin|A| + cos|A|`), never `from_blade_dict`, because a graded operand's own type can't hold the scalar part (a `Bivector3` cannot represent its own exponential — the dispatching `+` widens it to `Rotor3`, which is also what makes the generated narrowing override `Bivector_n.exp() -> Rotor_n` sound); and the `(A²).is_scalar()` guard is required even for *homogeneous* input, because a non-simple bivector of 𝒢ₙ (n ≥ 4, e.g. `e12 + e34`) is grade-2 yet has a non-scalar square. Landing `exp` also fixed a latent contract bug it exposed: the generated full classes' `__add__`/`__sub__` crashed on a bare number/`sympy.Expr`, violating `MultiVectorBase.__add__`'s documented contract. — `2026/07/29/exp-for-rotors.md`

- **`plane_rotation` builds its rotor by hand-written trig ON PURPOSE — do not "unify" it onto `exp()`.** The swap was implemented and measured (2026-07-29): `exp` must compute `|A| = sqrt((θ/2)²)` blindly, which (a) differs from `θ/2` by 1 ulp for ~11% of float angles (1,096/10,000 sweep), and (b) renders a merely-`real` symbolic θ as `cos(Abs(theta)/2)` instead of `cos(theta/2)`. `plane_rotation` knows two things `exp` cannot: its bivector is *unit*, and the half-angle's sign cancels by trig parity — so the hand-built closed form is the better implementation, not a violation of the "never hand-build a rotor" rule (which targets user code). Equivalence is permanently guarded by `tests/test_exp.py::test_exp_agrees_with_plane_rotation_{numeric,symbolic}`. — `tasks/plane-rotation-via-exp.md` (investigation record)

- **`match` is the house favourite, but genuine candidates are few — don't convert every conditional.** The code already uses `match` at every structural-dispatch site; remaining `if/elif` chains are predicate guards where `match` is churn, not clarity. Adopting `requires-python = ">=3.13"` (floor forced by `typing.TypeIs`) surfaced a latent bug: a string forward-ref `|`'d with a real type in project/reject/reflect that only worked by luck under old semantics. — `2026/06/05/use-match-and-modern-python.md`

- **The Python coding standard splits enforced-by-ruff from judgment-calls, and prose is spent only on the latter.** Don't re-prose PEP 8 layout / Pyflakes / import sorting / naming casing (ruff `N`, enabled with zero suppressions — generated code was already clean). Resolved tensions worth knowing: "inline a value used once *unless* the name documents an opaque expression"; the Scheme-style inner-fn shape is *preferred, not enforced* — don't churn existing early-return code. Hardened `TypeSpec` from an untyped `namedtuple` to `typing.NamedTuple` (the untyped version made `spec.blades` `Any`, so blade annotations were trusted, not ty-verified). — `2026/07/18/python-programming-standard.md`

## Coefficient views, display & simplify

- **Display (`_repr_latex_`) simplifies; `__repr__` stays raw.** Lazy classes should *show* lowest-terms coefficients without mutating stored fields, so `_repr_latex_` renders `self.simplified().to_blade_dict()`. `__repr__` is left as the raw dataclass repr on purpose — "the honest stored state for debugging." Cheap because display is not hot. — `2026/06/12/display-simplify.md`

- **`.simplified()`/`.expanded()` are real `MultiVectorBase` methods (map a sympy op over `to_blade_dict()`), chosen over notebook-local helpers.** Small, broadly useful, discoverable, and shared across display-simplify / bivector-dual / show-mult. — `2026/06/12/graded-bivector-dual-simplify.md`

- **To force a display *form* that survives `Gn`, transform the blade dict directly — never rebuild the multivector.** `nbplotutils._expand_numerators_dict` expands numerators but keeps denominators factored, working *without* `from_blade_dict`. An ABC `expanded_numerators()` was built first and *removed as dead*: rebuilding via `from_blade_dict` re-runs `Gn.__post_init__`'s eager `sympy.simplify`, which re-factors the just-distributed numerator back. This is why these helpers' tests target `[G1,G2,G3]`, not `Gn`. — `2026/06/15/show-mult-expand-numerators-not-denominators.md`

- **One unified blade sort key `(len(b), b)` across `__iter__`, `_repr_latex_`, `_blade_terms`.** Two keys (`(len(b), str(b))` vs `(len(b), b)`) *happen to agree only for single-digit indices* (n<10) and diverge at n≥10; `_blade_terms` had no sort at all. Also declined adding public `blade_terms()`/`coefficients()` iteration API — the need was met by extracting `base.blade_dict_latex(d)`. — `2026/06/12/show-mult-improvements.md`

## Correctness fixes worth remembering

- **`__rmul__` fall-through returns `NotImplemented`, not `-self._geometric_product(lhs)`.** The negation was wrong — the geometric product isn't anticommutative in general — and was dead code (scalars handled earlier, MV*MV via `__mul__`); returning `NotImplemented` gives a clean `TypeError`. Same doc: `reject`/`reflect` must use `outer_product_of_vectors(*sequence)`, not the 2-arg instance `outer_product` (which "works by luck for exactly two elements"). Grade-3+ rejection/reflection still hits a TODO `raise`. — `2026/06/05/correctness-bugs.md`

- **`|ab| = |a||b|` is kept as `|a|·|b|`, not `abs(a*b)` — the cleaner form is actively harmful.** `abs(a*b) = √(|a|²|b|²)` is a nested radical sympy **cannot simplify through the sandwich**, regressing the symbolic `R v R⁻¹ == rotate` identity (residual ~1e-138). Two simple sqrts stay tractable. A formal arbitrary-`n` proof was deliberately not pursued (2D/3D demos + "two vectors span one 2-plane" judged sufficient). — `2026/06/27/geometric-product-magnitude-proof.md`

## Doc-region markers

- **Marker names are descriptive and prefix-free — SHA1 was proposed then dropped.** Sphinx `literalinclude` matches the first line *containing* the anchor, so one name being a *prefix* of another silently selects the wrong region (demonstrated: `…-magnitude` rendered `…-magnitude-signature`, no warning). SHA1-of-*identity* (not content — a content hash rebreaks the book on every edit) was the first fix; the final decision is a uniform "one region per class + per method" pass whose trailing `class`/`method`/`setter` keyword makes names prefix-free by construction. `make check-regions` also checks for *exact* duplicates (invisible to a set-based prefix check — nearly missed an `x` getter/setter dup). Markers emit as sentinel string-literals rewritten to comments, since a comment can't live in an AST. — `2026/07/21/emit-doc-region-markers.md` (proposal), `2026/07/21/annotate-generated-doc-regions.md` (final)

## Packaging & dev workflow

- **The vendored Emacs `elpa/` tree is the source of truth; the image build is offline w.r.t. it.** Removed the build-time MELPA fetch and `.dockerignore`'d `elpa/`; `make update-emacs-packages` rebuilds, wipes+reinstalls, strips arch-specific `*.elc`/`*.eln`, and `git add -f`s. Note `.dockerignore` ≠ `.gitignore` — the "off-limits but tracked" rule is preserved. — `2026/06/07/emacs-package-install-strategy.md`

- **The Dockerfile bakes `dev` extras via a targeted source COPY, not `COPY .`.** `COPY .` would duplicate the 31M vendored Emacs tree into the image, and a `.dockerignore` can't fix it (it filters the build context globally, also breaking the legitimate `COPY entrypoint/dotfiles/`). The targeted COPY + `--no-build-isolation` also gives better layer caching and makes the package importable without the mount. — `2026/06/07/dockerfile-bake-dev-tools.md`

- **The container uses a `--system-site-packages` venv (mirroring mvp), fixing ty import resolution.** On Fedora, `uv pip install --system` split deps across `/usr/lib` (dnf) and `/usr/local/lib` (uv); ty keys off `sys.prefix=/usr` and never saw the `/usr/local` half → 3 spurious `unresolved-import`s. A venv makes ty key off `VIRTUAL_ENV`. — `2026/06/14/venv-consistency-with-mvp.md`

- **License is `LGPL-2.1-only`, chosen to match mvp's `pgzero_gl`.** mvp's LGPL-2.1-only `pgzero_gl` shim subclasses `gacalc.g2.Vector2`, so an LGPL gacalc makes the coupling license-clean. Unilaterally valid (single author across all 239 commits). Already-published PyPI ≤0.0.5 keep their prior GPL grant; the relicense applies from the next release — bump version first. — `2026/07/08/relicense-to-lgpl.md`

- **`image-export`/`image-import` gitignore the tar and have no `image` prerequisite.** The tars are multi-hundred-MB and must never be committed (mvp's copy omits this gitignore — don't inherit the gap). No `image` prereq so it errors clearly if you haven't built, rather than silently triggering a long rebuild. `save`/`load` start no container, so no `--cgroups=disabled` is needed nested. — `2026/06/16/image-export-import-targets.md`
