# Generate a type-correct sandwich (versor) operation: Rotor·Vector → Vector

**Created:** 2026-06-08 · **Completed:** 2026-06-08

## What landed

`Rotor{n}.sandwich(x)` is generated by `tools/gen_specialized.py` (the Rotor-only block of
`generate_graded_type`) via `dispatch_method` with `gn_op = lambda r, x: r * x * r.inverse()`. It
covers the **full grade-preserving family** — `Rotor·Scalar→Scalar`, `Rotor·Vector→Vector`,
`Rotor·Bivector→Bivector`, `Rotor·Trivector→Trivector`, `Rotor·Rotor→Rotor` — each returning the
operand's own type, because the other grades cancel symbolically and `resolve()` types the result
exactly. That went beyond the planned `Rotor·Vector` scope. `base.AbstractMultiVector.sandwich` stayed,
unchanged and under the same name, as the generic fallback for `Gn` and non-specialized types.

mvp's `transforms.rotor_rotation` runs on the generated `Rotor3.sandwich` closed form, with no runtime
projection. It landed in gacalc at version 0.0.3 and was installed into mvp's container venv
(github.com/billsix/modelviewprojection). Tests are in `tests/test_transforms.py`; 207 gacalc and 22 mvp
tests passed, ruff clean. The follow-up was `tasks/archive/2026/06/11/restore-ty-on-generated-sandwich.md`.

## The finding behind it (symbolic, 2026-06-08)

For a general even element `R = a_s + a₁₂e₁₂ + a₁₃e₁₃ + a₂₃e₂₃` and vector `v = v₁e₁ + v₂e₂ + v₃e₃` in
𝒢₃, the intermediate `R·v` has support `{1, 3}` (a real trivector,
`e₁₂₃ = a₁₂v₃ − a₁₃v₂ + a₂₃v₁` — why the geometric product widens), but the full `R v R⁻¹` has support
`{1}` only: the `e₁₂₃` coefficient is identically zero (likewise for `R v R̃`). The vector coordinates
are quadratic in the rotor's and linear in the vector's, over `|R|²` for the inverse form. Treating the
sandwich as one derived operation, instead of two widening products, makes its output provably grade 1,
so the generator types it natively. That replaced the hand-written runtime projection for the
specialized classes, and it shows students why a rotor sandwich yields a vector.

It complements the odd `{1,3}` type (`tasks/archive/2026/09/05/model-odd-graded-type.md`), which fixes
the geometric product `Vector3 * Bivector3` (genuinely vector + trivector); the derived sandwich fixes
the rotation (purely a vector). Both were wanted.

## Decisions (William Emerison Six <billsix@gmail.com>, 2026-06-08)

- **`R v R⁻¹`, accepting rational coefficients** (the `/ |R|²` denominator, factored by `cse`), rather
  than the polynomial `R v R̃`, which is a rotation only for a unit rotor.
- The method was named `sandwich`, matching the existing generic.
- The original scope was `Rotor·Vector`, with other grades deferred to
  `tasks/archive/2026/11/09/generalize-sandwich-other-grades.md`; the generator delivered the full
  grade-preserving family for the rotor operand here.

## The ty wrinkle and its fix

The generated `numbers.Real` sandwich arithmetic (division by `|R|²`, quadratic `self*self` terms) gave
false `unsupported-operator` positives, and the generated `sandwich`'s `typing.Self` return tripped
`invalid-method-override` against the ABC. Because the generator renders via `ast.unparse`, it cannot
carry inline `# ty: ignore` comments. The fix was a narrow `ty.toml` `[[overrides]]` scoped to
`g2.py`/`g3.py` disabling only those two rules, proven narrow (an injected undefined name was still
caught). Inline comments were rejected: ty warns on unused ignores (so generation would need a ty run to
find exact lines) and `g*.py` is ruff-linted (so it would need `# noqa: E501` too) — fragile,
tool-version-coupled generation.
