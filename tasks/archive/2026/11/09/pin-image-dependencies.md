# Pin the image's dependencies without pinning the library's consumers

**Priority:** 7
**Difficulty:** 3
**Created:** 2026-11-09
**Source:** tasks/review/2026/11/08/repo-review.md §8.1

## Summary

Before this task, two `make image` runs months apart could resolve different versions: the image
installed from `pyproject.toml`'s loose list, and `pyright` was npm-installed unpinned. Now the image
installs from a committed constraints file and a pinned pyright, and `pyproject.toml` stays loose
for consumers.

## Decisions

1. A constraints file regenerated by a `make update-pins` target, not a `uv lock` lockfile
   (William Emerison Six <billsix@gmail.com>, 2026-11-09).

## What was done

- `constraints.txt` (156 pins) was generated with `uv pip compile pyproject.toml
  entrypoint/image-requirements.in --extra dev --extra notebooks --extra jupyter` against the image's
  `/venv/bin/python`. `entrypoint/image-requirements.in` lists the image-only packages (setuptools,
  wheel, and the Sphinx set).
- The `Dockerfile`'s late dependency layer copies `constraints.txt` and installs with
  `-c constraints.txt`, re-installing setuptools/wheel and (under `BUILD_DOCS`) the Sphinx set under
  the constraints. The earlier, slower layers stay unpinned, so a pin bump rebuilds only the late
  layer.
- `entrypoint/01-install-base.sh` installs `pyright@1.1.414`; the `Makefile`'s check-notebooks
  comment now says so.
- `make update-pins` (`## `-documented) regenerates `constraints.txt` in the container.
- `CLAUDE.md` › "Dev workflow" documents the pin file and the bump path.

## Verification

A full nested rebuild with the pins: `make image` exit 0, `make test` 775 passed / 2 skipped,
`make check-notebooks` 0 errors. A `uv pip freeze` of the built image matched every pin in
`constraints.txt`; its only unpinned packages are `pip` (from the venv) and `nanobind` (installed
by `entrypoint/install-epix.sh` for the ePiX extension, pinned by `EPIX_COMMIT`'s build). `npm ls -g`
reported `pyright@1.1.414`.
