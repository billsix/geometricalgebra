# Pin the image's dependencies without pinning the library's consumers

**Status:** proposed — needs go-ahead
**Priority:** 7
**Difficulty:** 3
**Created:** 2026-11-09
**Source:** tasks/review/2026/11/08/repo-review.md §8.1

## BLUF

Two `make image` runs months apart can resolve different Python and npm versions. That is because the
image installs straight from `pyproject.toml`'s loose dependency list, and `pyright` is npm-installed
unpinned. Done means the image installs from an exact, committed pin set (a constraints or lock file
the Dockerfile alone uses, plus a pinned `pyright`), `pyproject.toml` stays loose for consumers, and
`make image` plus `make test` pass.

## Context

Read first: the personal overlay's "Python deps — prefer distro `python3-*` for the heavy/native
ones; pin everything; `--system-site-packages`", and its "Self-contained images + live source".

- **The finding (LEAD/convention):** `pyproject.toml` leaves every dependency loose, on purpose for
  consumers ("a library shouldn't force exact versions"). The Dockerfile installs `-r pyproject.toml`,
  and `entrypoint/01-install-base.sh` npm-installs pyright with no version. An exported image is
  unaffected (it is self-contained); a rebuild isn't reproducible.
- **The usual fix:** a constraints file (`uv pip compile pyproject.toml --all-extras -o
  constraints.txt`, then `uv pip install -r pyproject.toml -c constraints.txt`) pins the image without
  touching consumers. Distro-provided packages (`python3-numpy`, `python3-sympy`, …) are pinned to the
  versions Fedora ships, read from the built image, so pip sees them as already satisfied.
- **Watch for:** a pin that installs a different version than requested is a conflict to surface (the
  personal overlay's moviepy incident). The `USE_LEAN` Mathlib bake and the ePiX `EPIX_COMMIT` are
  already pinned.

## Plan

- [ ] List what the image installs now: `uv pip freeze` in the built image, and `npm ls -g`.
- [ ] Generate the constraints file, wire it into the Dockerfile's pip step, and pin `pyright@<version>`
  in `01-install-base.sh`.
- [ ] Add `make update-pins` (`## `-documented) that regenerates the constraints file in the
  container (the bump path).
- [ ] `make image`, `make test`, `make check-notebooks`; check that the frozen versions match the pins.
- [ ] Document the pin file and how to bump it in `CLAUDE.md` › "Dev workflow".

## Decisions

1. Use a constraints file regenerated by a `make update-pins` target, not a `uv lock` lockfile
   (William Emerison Six <billsix@gmail.com>, 2026-11-09).
