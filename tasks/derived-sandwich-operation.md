# Generate a type-correct sandwich (versor) operation: Rotor·Vector → Vector

Status: **plan — not started** · proposed 2026-06-08 · needs a go/no-go

## Goal

Add a **derived sandwich / versor-conjugation operation** to gacalc, generated by
`tools/gen_specialized.py` exactly like the geometric/inner/outer products: a
generic `Gn` form plus closed forms specialized per dimension. For now, scope to
**`Rotor.sandwich(Vector) → Vector`** (what rotations need). Because the operation
is *derived as a whole* (`R v R⁻¹`), its symbolic output is grade-1, so the
generator types it as `Vector` natively — **no runtime grade projection**.

## Finding (the proof, done symbolically 2026-06-08)

For a fully general even element (rotor) `R = a_s + a₁₂e₁₂ + a₁₃e₁₃ + a₂₃e₂₃` and
a general vector `v = v₁e₁ + v₂e₂ + v₃e₃` in 𝒢₃:

- The **intermediate** `R·v` has support `{1, 3}` — a real trivector:
  `e₁₂₃ = a₁₂v₃ − a₁₃v₂ + a₂₃v₁`. (This is why the geometric product widens.)
- The **full sandwich `R v R⁻¹`** has support **`{1}` only** — the `e₁₂₃`
  coefficient is **identically zero** (it cancels symbolically, not just
  numerically). Likewise `R v R̃`.
- The vector coords come out as the expected closed form — quadratic in the
  rotor's coords, linear in the vector's, e.g.
  `e₁ = (a_s² − a₁₂² − a₁₃² + a₂₃²)v₁ + 2(…)v₂ + 2(…)v₃`, all over `|R|²` for the
  inverse form — the same *shape* as the geometric product.

**Conclusion:** treating the sandwich as its **own derived operation** (not two
separate geometric products, each of which legitimately widens) makes its output
provably grade-1. The generator's `resolve()` then types it as `Vector`. This is
strictly better than the current hand-written `base.sandwich` runtime projection.

## Decisions (Bill, 2026-06-08)

- **Use `R v R⁻¹`** (the inverse form — the true rotation for any rotor),
  **accepting the rational coefficients** (the `/ |R|²` denominator), rather than
  the polynomial `R v R̃` (which would be the rotation only for a unit rotor).
- **Scope to `Rotor·Vector → Vector`** for now. Other grades (e.g.
  `Rotor·Bivector → Bivector`) are deferred — see
  `tasks/generalize-sandwich-other-grades.md`.

## How it drops into the generator

The machinery already supports it — `product_result(t1, t2, gn_op, …)` takes *any*
binary `gn_op(A, B)`:

- Define `gn_op = lambda R, v: R * v * R.inverse()`.
- `product_result(Rotor{n}, Vector{n}, gn_op, …)` derives the closed form over the
  rotor's symbols (`coeff_scalar`/`coeff_e_12`/…) and the vector's
  (`coeff_e_1`/…). The result's nonzero support is `{1}` (the `e₁₂₃` coefficient
  simplifies to 0 and is pruned), so `resolve()` returns `Vector{n}`.
- Emit a `sandwich` method on the `Rotor{n}` class (a `match` on the operand
  type, returning the closed-form `Vector{n}`), mirroring how
  `_geometric_product` / `inner_product` / `outer_product` are emitted.
- `cse` factors out the shared `|R|²` denominator, so the rational arms stay
  readable.

**Generic vs specialized** (like the products): `Gn`/the ABC keeps the existing
generic `sandwich` (`base.AbstractMultiVector.sandwich`, which computes
`self * x * self.inverse()` and rebuilds as `type(x)`); the generated
`Rotor2.sandwich(Vector2)` / `Rotor3.sandwich(Vector3)` are the fast, type-correct
closed forms that *override* it for those classes — so for the specialized types
there is no `from_blade_dict` projection at all.

## Impact

- `Rotor3.sandwich(Vector3)` returns a `Vector3` by construction — the runtime
  grade projection in `base.sandwich` is no longer exercised for the specialized
  classes.
- mvp's `transforms.rotor_rotation` / the rotations stay exactly as they are
  (thin wrappers), but are now backed by a type-correct closed-form sandwich.
- Great teaching artifact: the symbolic derivation *shows* the `e₁₂₃` terms
  cancel — students see *why* a rotor sandwich yields a vector.

## Complementary to the odd-`{1,3}` type

This is **not** a replacement for `tasks/model-odd-graded-type.md`:

- The **odd `{1,3}` type** fixes the *geometric product* `Vector3 * Bivector3`
  (which genuinely is a vector + trivector) — type completeness.
- The **derived sandwich** fixes the *rotation* `R v R⁻¹` (which is purely a
  vector) — type correctness without projection.

Do both; they address different operations.
